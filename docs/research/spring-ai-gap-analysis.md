# Spring AI research vs. the JordyLab AI code: gap analysis

Date: 2026-10-05. Compares `docs/research/spring-ai-architecture.md` (the report, section numbers below) with the code that
exists today: `ResilientAiService` and its package (`jordylab-be/src/main/java/dev/jordy/jordylab/shared/ai/`), its three
callers (`fna/service/BriefingGeneratorService`, `gamecatalog/service/EnrichmentService`, `gamecatalog/service/ChatService`),
`src/main/resources/application.yaml` and `src/main/resources/prompts/`. Nothing here changes behaviour; each verdict is
a decision input. Gaps worth building have a draft under `specs/_drafts/`; gaps that only matter once a module exists are
marked defer with the module that would trigger them (spec 012, clarification Q4).

Verdicts: **build** (worth building now), **defer** (revisit when the named module or condition exists), **n/a** (already
covered, or does not apply to this repo).

| # | Topic (report §) | What the report says | What the repo does (checked in) | Verdict | Reason / next step |
|---|---|---|---|---|---|
| 1 | Retry (§6) | One retry layer; vendor SDKs retry themselves in 2.0 | OpenAI and Anthropic modules use the SDKs' own retries; `ResilientAiService` adds exactly one retry on another provider (`call` → `tryGateway` → `attempt(FALLBACK)`) | n/a | One layer plus a provider hop; nothing stacked. Keep. |
| 2 | Provider fallback (§6) | Spring AI ships none; use a gateway or a CB fallback | OpenRouter gateway first, Anthropic `claude-sonnet-5` on any failure; per-feature model via Settings (`ResilientAiService.tryGateway`, `ConfiguredAiModelResolver`) | n/a | Done, and better than the report's baseline. |
| 3 | Circuit breaker, bulkhead, timeout (§6) | Resilience4j around the adapter | Timeout: 120 s per call on a virtual thread (`callWithTimeout`). Breaker: `ProviderHealthCache` skips a failing provider for 30 s (`health-check-ttl-seconds`). Bulkhead: none (unbounded concurrent calls) | defer | A single-user app with scheduled batch work does not need a concurrency cap. Revisit if a user-facing AI endpoint is exposed to more than the admin. |
| 4 | Token budgets and cost limits (§6, §8 LLM10) | Token-budget advisor, usage metrics, gateway quotas | `jordylab.ai.calls` counts calls and outcomes only; `AiCallCompleted` carries no token usage; no per-feature budget; the OpenRouter credit ran out once (HANDOFF-08, spec 011) | **build** | Record input/output tokens per call and alert/stop on a configurable daily budget. Draft: `ai-token-usage-and-budget`. |
| 5 | Typed outputs with validation (§4.1, §7.4) | Return a typed record and validate immediately; optionally provider-native schema | Enrichment parses JSON by hand into `EnrichmentFacts` with bounds checks (`parseAndValidate`); chat translation is validated against the visible platforms and hosts (`parseFilter`); briefing stores free text. `ResilientAiService` returns a `String` | defer | Validation exists where output drives behaviour. Provider-native structured output would change the `ResilientAiService` contract for little gain now; revisit with the next new feature that needs a schema. |
| 6 | Prompts as versioned resources (§7.2) | Prompts in `classpath:/prompts/*.st` | Only the briefing prompt is a resource (`prompts/fna/briefing-system.st`); enrichment (`EnrichmentService.SYSTEM_PROMPT`) and chat (`ChatService.TRANSLATION_SYSTEM_PROMPT`, `COMPOSITION_SYSTEM_PROMPT`) are Java text blocks | **build** | Move the three prompts to resources like the briefing one. Draft: `ai-prompts-as-resources`. Versioning/trace-id of the prompt stays out of scope (community convention, not first-party). |
| 7 | No model call inside a transaction (§7.3) | Write intent in the transaction, call the model after commit, make handlers idempotent | `BriefingGeneratorService.generateBriefing` is `@Transactional` and calls `aiService.call` inside it. `EnrichmentService.enrichPending` is `@Transactional` and runs up to `batchSize` sequential AI calls in one transaction (each up to the 120 s timeout, plus the fallback attempt), and it is itself called from two other transactions: `ScanService.submitScan` (via `populateCatalogData`, the ingest endpoint) and `SteamLibrarySyncService.syncOwned`. `ChatService` is not transactional | **build** | A database connection is held for the length of the model calls, a scan upload and its response wait on them (the code comment already caps the batch to avoid the client's read timeout), and a late failure rolls back unrelated updates. Draft: `ai-calls-outside-transactions`. |
| 8 | Tool authorization and least privilege (§5.2, §8 LLM06) | `ToolContext`, call limits, authorization inside secured services | No `@Tool`, MCP or tool calling anywhere | defer | Trigger: first feature that gives a model tools (recipe or trading assistant). | 9 | Human approval for write actions (§5.2, §8) | Not shipped by Spring AI; build approve/resume | No AI write path exists. Trading requires approval by repo rule | defer | Trigger: the `trading` module. |
| 10 | Observability content logging (§10) | Prompt/completion/tool content off by default | No `spring.ai.*.observations.log-*` property set anywhere, so content logging is off; call outcomes are logged without prompts (`ResilientAiService` log lines carry feature, provider, model, reason). | 11 | Observability metrics (§10) | Micrometer `gen_ai.*` metrics, token usage | `jordylab.ai.calls` counter and `AiCallCompleted` event exist; `/actuator/metrics` is exposed | covered by #4 | The missing part is token usage, handled in the budget draft. |
